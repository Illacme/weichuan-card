## 同时验证的失败路径（这些比「通过」更重要）

| 场景 | 期望 | 实测 |
|---|---|---|
| 有 `runtime.env` 但未设 `BACKUP_ENC_KEY` | 整次失败，且**不留任何产物** | ✅ 退出码 1，备份目录为空 |
| 用错误口令恢复密钥包 | 硬停，**不把垃圾写进 `runtime.env`** | ✅ 退出码 1，未写出文件 |
| 密钥包是否含明文 | 不应出现 `PII_ENC_KEY` / `ADMIN_PASS` 的值 | ✅ `grep` 未命中 |
| 备份→恢复一致性 | 逐字节一致 | ✅ 图片 / `runtime.env` / `license.key` 全部 `cmp` 通过 |
| 覆盖密钥前是否留安全网 | 旧 `runtime.env` 另存 | ✅ `backups/pre-restore-secrets-<时间戳>/` |
| 容器形态（`docker cp` 写卷） | 新容器也能恢复 | ✅ 两容器间内容比对一致 |

## 结论与后续

- 备份链路可用：归档未损坏、库能打开、表齐、图片与密钥都能解开。
- 本次仍是**单实例、少量数据**演练，未覆盖「大库（GB 级）恢复耗时」与
  「恢复期间服务可用性」——需在预发环境用贴近生产的数据量再跑一次并记录 RTO。
- **待运维执行**：生产环境需先设 `BACKUP_ENC_KEY`（`openssl rand -base64 24`），
  并把口令单独保管；否则 `backup.sh` 会拒绝产出备份（这是刻意的，见 runbook §9.2）。
- 演练节奏：每季度一次；改备份脚本 / 换部署形态后补跑。
